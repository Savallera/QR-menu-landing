# Правила работы с проектом

## Язык общения

Рассуждай и отвечай пользователю на русском языке, если пользователь явно не попросил использовать другой язык.

## Порядок работы и согласование

По умолчанию выполняй задачу без отдельного согласования: сначала изучи контекст и кратко опиши действия в чате, затем приступай к работе.

1. Сначала изучи задачу, текущий код и макет, если он есть. Соразмеряй глубину анализа и подробность плана с задачей.
2. Напиши в чате, что обнаружено, что будешь менять, какие существующие решения используешь и как проверишь результат. Укажи существенные расхождения макета с системой проекта. Если согласование явно не запрошено, продолжай работу без ожидания ответа.
3. Ожидай согласования только тогда, когда пользователь прямо просит об этом в тексте задачи: например, «согласуй со мной», «сначала согласуем», «дождись моего подтверждения», «не меняй без моего одобрения» или другой формулировкой с тем же смыслом. В таком случае сначала представь анализ и план, затем дождись явного одобрения перед изменениями. Утверждённые шаги выполняй без повторных запросов; существенное изменение такого плана согласуй заново.
4. Если пользователь запросил только анализ, план или ревью, ограничься этим результатом: такой запрос сам по себе не поручает реализацию.

## Правила вёрстки

Эти правила согласованы с пользователем. Применяй их при создании и изменении страниц, блоков, стилей и поведения интерфейса.

1. **Сначала изучай существующее решение.** Перед изменениями просмотри аналогичные страницы, нужные блоки и базовые стили в `src/styles`. Ориентир — система проекта и согласованные решения; отдельные старые исключения не считай образцом для нового кода. Адаптируй макет к существующим компонентам, переменным и типографике. Не заменяй значение из макета ближайшей переменной автоматически: оцени влияние на плотность, пропорции, переносы и удобство. О заметных расхождениях сообщай до реализации. Небольшое отличие от макета предпочтительнее дублирующих стилей; если система не позволяет решить задачу без ухудшения интерфейса, обоснуй необходимое дополнение.

2. **Соблюдай структуру проекта.** Страницы размещай в `src/pages`, блоки — в `src/blocks`. Для блока используй отдельную папку с HTML, `_имя-блока.scss` и JS, если нужно поведение. Подключай разметку через существующие `@@include`, стили — через `src/styles/styles.scss`, JS — через соответствующую точку входа в `src/scripts`.

3. **Соблюдай БЭМ.** Используй синтаксис `block`, `block__element`, `block_modifier_value`, `block__element_modifier_value`. Модификатор добавляй вместе с базовым классом. Элемент должен принадлежать своему блоку в разметке.

4. **Не заимствуй элементы чужих блоков ради оформления.** Например, вне блока `theme` используй собственные `contact-details__card` и `contact-details__card-title`, а не `theme__card` и `theme__card-title`. Самостоятельные переиспользуемые блоки, например `button`, можно размещать внутри других блоков и смешивать с их классами.

5. **Переиспользуй общие решения целиком.** Перед созданием класса или скрипта ищи готовое решение. Используй существующие блоки с их разметкой, элементами, стилями и поведением. Повторяющиеся оформление и поведение выделяй в общий блок в `src/blocks`; уникальное оформление оставляй в блоке страницы. После переноса удаляй прежние классы, стили, обработчики и подключения, которые больше не используются.

6. **Стилизуй через классы.** Оформление храни в SCSS соответствующего блока. Не добавляй статические инлайн-стили, ID-селекторы и новые глобальные правила для HTML-тегов ради конкретной страницы. Динамические значения из JS допустимы при обоснованной необходимости, например для измеренной высоты или положения; они не должны дублировать оформление из SCSS. Временные значения очищай после завершения эффекта. Избегай зависимости от случайного порядка элементов. Сначала исправляй структуру и каскад, прежде чем повышать специфичность селекторов или применять `!important`.

7. **Используй переменные по назначению.** Цвета, типографику, отступы, скругления и тени бери из `src/styles/_variables.scss`. Например, `--indent-*` предназначены для отступов, `--text-*` — для текста. Не используй переменную отступа как основу расчёта размера иконки. Не добавляй произвольные цвета и параллельную систему параметров оформления.

8. **Задавай размеры просто.** Используй `rem` для размеров, связанных с базовым масштабом страницы, и `em`, когда размер должен зависеть от шрифта элемента. Для иконок используй прямые значения, например `1.5rem` и `3rem`, без вычислений через переменные отступов. Для `gap` и `padding` выбирай готовые переменные отступов; не умножай и не дели их через `calc()` ради совпадения с числом из макета. `calc()` применяй там, где действительно нужна зависимость размеров или компенсация отступа.

9. **Сохраняй типографику проекта.** Используй локальный Raleway и существующую шкалу размеров. Учитывай начертания, межстрочный интервал и иерархию заголовков. При изменениях подключения шрифта проверяй корректность диапазона начертаний в `@font-face`. Новые шрифты и удалённые подключения добавляй только по отдельной задаче.

10. **Сохраняй систему секций и отступов.** Используй `section`, `section__indent`, существующие ограничения ширины и переменные контейнеров. Различай внешний отступ подложки и внутренний отступ контента: фон должен обрамлять текст и иконки с достаточным пространством. Не создавай параллельную систему сетки и размеров страницы.

11. **Используй существующую адаптивность.** Применяй `@include media(...)` и брейкпоинты из `src/styles/_mixins.scss`: `xs` — `30em`, `sm` — `36em`, `md` — `48em`, `lg` — `64em`, `xl` — `76.5em`, `xxl` — `114em`. Проверяй переносы и поведение около точки перестроения. Учитывай текущую минимальную ширину проекта — 360 px. Исключай горизонтальное переполнение, обрезанный текст и фиксированную высоту текстовых блоков, мешающую росту содержимого.

12. **Учитывай переводы и RTL.** Предпочитай логические свойства: `padding-inline`, `margin-block`, `inline-size`, `text-align: start`. Оставляй место для более длинных переводов. Сохраняй `notranslate`, `translate="no"` и `dir="ltr"` у реквизитов, телефонов и других подходящих данных. Сохраняй существующую логику выбора языка и переходов между страницами.

13. **Используй существующие изображения и иконки.** Сначала ищи нужный ресурс в проекте. Иконки, включая галочки и другие служебные значки, подключай из общего SVG-спрайта с корректным `viewBox`; не заменяй имеющуюся иконку текстовым символом. Не импортируй заново уже имеющиеся ресурсы. При сборке спрайта проверяй уникальность идентификаторов, полноту набора и отсутствие стилей, влияющих на соседние иконки. Оптимизация SVG не должна менять рисунок. Новый ресурс добавляй только при отсутствии подходящего и необходимости по задаче; изображения оптимизируй для веба с проверкой качества и размера файла.

14. **Сохраняй содержание и поведение.** Тексты, реквизиты, тарифы и адреса ссылок меняй только по прямому запросу. Используй семантические ссылки и кнопки, видимый фокус, доступные подписи и уведомления. Переключение цветовых тем самостоятельно не добавляй: его внедрение пользователь не заказывал. Светлые и тёмные подложки секций не являются переключением темы.

15. **Редактируй исходники и проверяй результат.** Изменения вноси в исходники, затем обновляй `dist` существующей сборкой. Не исправляй проблему только в сгенерированной копии. Для генерируемых документов учитывай их источник и генератор. Проверяй затронутые страницы на компьютере и телефоне: переполнение, переносы, отступы, ссылки и состояния элементов. Для общих блоков проверяй несколько страниц; для поведения — соответствующие сценарии и тесты. Масштаб проверки должен соответствовать изменению. В отчёте отдельно сообщай о браузерной проверке и существующих автотестах, указывай проверенные сценарии и оставшиеся ограничения.

16. **Сохраняй границы задачи.** Учитывай текущие пользовательские изменения и не откатывай несвязанные правки. Не форматируй весь файл ради точечной правки. Не меняй соседние компоненты и общие переменные без необходимости для задачи. Убирай созданные временные файлы проверки. В конце кратко сообщай, что изменено и что проверено. Публикацию в Git, на сервер или GitHub Pages выполняй по отдельному запросу. Основной сайт — `showme.menu`; GitHub Pages используется для презентации. Не адаптируй пути публикации без указания пользователя.

17. **Учитывай поведение анимаций.** Для анимаций появления и аккордеонов используй согласованные 320 мс, если задача не задаёт другое значение. Учитывай `prefers-reduced-motion`, отмену анимации и быстрые повторные действия. После завершения или отмены очищай временные состояния и больше не нужные обработчики. Контент должен оставаться доступным без JS.
